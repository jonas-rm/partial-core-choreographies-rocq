\begin{abstract}
  Programming communicating processes is challenging, because it requires writing separate programs that perform compatible send and receive actions at the right time during execution.
  Leaving this task to the programmer can easily lead to bugs.

  \emph{Choreographic programming} is a paradigm that addresses this challenge by equipping developers with high-level abstractions for codifying the desired structures of communications among processes from a global viewpoint.
  Given a choreographic program (called \emph{choreography}), implementations of the involved processes can be automatically compiled by a process known as \emph{endpoint projection (EPP)}.

  While choreographic programming removes the possibility of manual mistakes in the implementation of communications with local send and receive actions, the correctness of a choreographic programming framework crucially hinges on the correctness of its compiler.
  Since choreography compilation is technically involved, previous efforts developed mechanisations of theories of choreographic programming and proved them correct in theorem provers.
  In this paper, we build on one of these formalisations to construct a toolchain that produces executable code from a choreography.

  \keywords{Choreographic programming \and Certified compilation \and Jolie \and Formal verification}
\end{abstract}

\section{Introduction}

In traditional distributed programming, the programmer is tasked with writing the implementation of each \emph{process} (endpoint) as a separate program, taking care of correctly matching send and receive actions in the different programs.
This approach is known to be cumbersome and error-prone \cite{LLLG16}.

\emph{Choreographic programming} \cite{M13p} is an alternative paradigm for distributed programming, where developers are equipped with high-level abstractions to specify the desired communications between processes from a global viewpoint.
Given a choreographic program (called \emph{choreography}), correct implementations of all of the involved processes can then be automatically generated by means of a compilation procedure known as \emph{endpoint projection (EPP)}~\cite{M23}.
This removes the possibility for manual mistakes in the programming of communication actions and provides important theoretical advantages, like deadlock-freedom by design -- the distributed code generated from a choreography is always deadlock-free, since it is syntactically impossible to write unmatched communications in a choreographic programming language~\cite{CM13}.
In addition to these correctness advantages, this also saves time and lets the programmer focus on the bigger picture of the protocol being developed.

Defining and implementing EPP is technically involved~\cite{SY19}, which motivated substantial efforts in the mechanisation of theories of choreographic programming using interactive theorem provers~\cite{CMP21,CMP21b,PGSN22,HG22}.
Among these, the formalisation of the choreographic programming language \emph{Core Choreographies (CC)} and its EPP to the process calculus of \emph{Stateful Processes (SP)} was designed with broad applicability in mind~\cite{CMP22}.
Specifically, its design allows for annotating communications with arbitrary metadata and is parametric on the languages used to express local computation, data, process identifiers, etc.

In this work, for the first time, we reap the benefits of~\cite{CMP22} to develop \toolname{} (pronounced `hack'): a tool for compiling choreographies in CC to executable code.
As target language for this executable code, we use the service-oriented programming language Jolie~\cite{MGZ14}.
Additionally, \toolname{} is designed with future extensibility in mind, so that new target languages can be added.

More technically, \toolname{}'s architecture consists of two compilation phases (\cref{fig:arch}).
The first phase (projection) uses EPP to translate a choreography into an abstract representation of process programs given in SP, which we use as an intermediate representation (IR).
This phase is certified: it is implemented by Haskell code that we extracted from the Coq formalisation of EPP in~\cite{CMP21b}.
The second phase (code generation) takes care of translating the abstract send and receive actions in the IR into code in an executable programming language.
In our current implementation for Jolie, this phase is not formally verified.
Nonetheless, it is a homeomorphic transformation that follows the term structure of the IR in a straightforward mechanical fashion.

Our development thus allows for coding and executing choreographies given in a well-understood language (CC)~\cite{CM20,CMP21,CMP21b,M23}.
Also, it confirms the informal claim made in~\cite{CMP22} that the formalisation of CC was made with flexibility in mind for this kind of applications.
In particular, our application to Jolie did not require any modification to the formalisation, but just an appropriate instantiation of its parameters and a simple interfacing of its extracted data types with the other components of our compilation pipeline in Haskell.

\paragraph*{Related work.}

There are two other formalisations of choreographic programming in the literature.

Kalas~\cite{PGSN22} is a choreographic programming language formalised in the Hol4 proof assistant.
It comes with an end-to-end certified compiler that targets CakeML~\cite{MO12}, a formally-verified subset of the ML language.
By contrast, we take a technology-agnostic approach that allows for reusing our compiler infrastructure for different target languages.

Pirouette~\cite{HG22} is a functional choreographic programming language formalised in Coq, which similarly to~\cite{CMP21} can be instantiated with different languages for local computation.
However, it has not yet been used to implement a choreographic compiler that targets executable code.

\section{Architecture and Implementation}
\label{sec:arch}

\paragraph*{Architecture.}

We implemented \toolname{} in Haskell and took a two-phased approach in the design of its compilation pipeline, shown in \Cref{fig:arch}.

The first phase is the \textit{projection}: it takes as input a choreographic program given as a CC term and projects it to a collection of SP terms representing the necessary behaviours of the endpoints.
We use SP as an intermediate representation (IR) of processes.
This part of the compiler uses the formally verified projection procedure that has been automatically extracted from the Coq formalization into Haskell code.
Making use of the extracted code is relatively straightforward, although a few considerations are necessary given that Coq is a dependently-typed language, while all of the languages it can extract to are not.

The second phase of our compiler is the \textit{code generation}: compiling the generated process IR to an executable language.
In this work we focus primarily on generating Jolie code.
However, because of our modular two-phase approach, additional backends could be implemented without having to touch the rest of the compiler.
This phase of the compiler is not formally verified, but its correctness is much easier to establish than the correctness of projection itself since the code generation proceeds homeomorphically \todo{``proceeds homeomorphically'', is this right} on the structure of the process IR.

\paragraph*{Implementation.}

The Coq formalization we use is parametric over the types used to represent process identifiers, variables, terms of the underlying expression language, terms, etc.
Because this is done by using the dependently-typed features of Coq and manipulating types as normal values, certain ``artefacts'' appear in the code extracted from Coq into Haskell.
In particular, instead of using Haskell's type system and parametric polymorphism, the extracted code makes use of GHC's \todo{cite maybe} \hc{Any} type and the \hc{unsafeCoerce} function to perform casts between the provided concrete types and \hc{Any} which the extracted code works on.
While a little clunky to work with, this is not an issue since the only requirement the formalization imposes on the type parameters is that their equality be decidable.
Practically, this means that we just have to be able to provide a function that can determine whether two values of such a type are equal.
Other than that the extracted code treats all of the type parameters as completely opaque.
For this purpose we wrote a thin wrapper over the extracted code that provides a much more pleasant and idiomatic API to work with, hiding the necessary casts and using Haskell's parametric polymorphism.
Again, this part is not formally verified, but just as before, the wrapper follows the structure of the CC and SP terms so checking it for correctness manually is easy.

Our reusable projection phase has the following Haskell interface.
We fix the types of process identifiers (\hc{Pid}), variable names (\hc{Var}, \hc{RecVar}), selection labels (\hc{Label}) and annotations (\hc{Ann}) for simplicity's sake.
Annotations serve a special purpose and will be explained shortly.
All of the mentioned types are just wrappers around \hc{String}s and only serve the purpose of being an identifier that can be compared for equality.
The parametricity that is re-exposed to the user are the types used to represent terms of the expression and boolean expression languages.

\begin{haskelllisting}
data Eta e
  = Com Pid e Pid Var
  | Sel Pid Pid Label

data Choreography e b
  = CEnd
  | Interaction (Eta e) Ann (Choreography e b)
  | CCond Pid b (Choreography e b) (Choreography e b)
  | CCall RecVar

newtype CDefSet e b = CDefSet [(RecVar, Choreography e b)]
newtype CProgram e b = CProgram (CDefSet e b, Choreography e b)

data Behaviour e b
  = BEnd
  | Send Pid e Ann (Behaviour e b)
  | Recv Pid Var Ann (Behaviour e b)
  | Choose Pid Label Ann (Behaviour e b)
  | Offer Pid (Maybe (Ann, Behaviour e b)) (Maybe (Ann, Behaviour e b))
  | BCond b (Behaviour e b) (Behaviour e b)
  | BCall (RecVar, Pid)

newtype BDefSet e b = BDefSet [((RecVar, Pid), Behaviour e b)]
newtype Network e b = Network [(Pid, Behaviour e b)]
newtype BProgram e b = BProgram (BDefSet e b, Network e b)

epp :: CProgram e b -> Maybe (BProgram e b)
\end{haskelllisting}
